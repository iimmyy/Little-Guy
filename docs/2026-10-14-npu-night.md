# Night of 2026-10-13/14: his whole 2-bit brain on the NPU

Raw notes and numbers (board Q6A, QCS6490 Hexagon v68, RAM at 3196.8 MHz, brain mix-21 + dictionary preview, 4 big cores for the CPU parts). Fork commits d2fbdeb .. f28ec6f.

## Starting point (evening)

- The engine's own NPU backend could only run matrix math on this chip: ADD, MUL, RMS_NORM, SCALE and ROPE killed the NPU program (`dspqueue_read failed 0x2e`).
- It had no 2-bit (Q2_K) support at all.
- 4-bit brain, matrix math on the NPU: 4.14 words/s vs CPU 5.99.
- Our own 2-bit NPU loop (Oct 10) streamed 15.5 GB/s at 46 °C peak vs the CPU's 16.0 GB/s at 79 °C (heat test, fan not on the NPU).

## What was wrong and what fixed it

| Problem | How it was found | Fix |
|---|---|---|
| NPU program died on small ops | bisecting with early returns (the file trace lost its last lines when the program died) | v68 dies on DMA writes from scratch memory to DDR and on DMA started from the callback thread: those copies are HVX vector copies now |
| A full brain ran at 0.5 words/s | per-op profile: every op ~2 ms | my own debug trace writes were in the hot path (each one a round trip to the board's files) |
| 2-bit kernel at 2 GB/s | timing inside the NPU | quantized inputs had been put in scratch memory (VTCM), where scalar loads stall: moved to cached memory, 10x faster |
| Inputs quantized slightly differently from the CPU | a check against the CPU's exact rule on 13.8 million values | v68 has no IEEE vector float math and qf32 cannot hold the magic-number trick: rounding is done with integer ops, 0 differences |
| Attention re-read the chat memory 4 times | reading the code | grouped-query attention: each memory block read once for the 4 heads that share it |
| 2-bit math as slow as the copy | timing copy-only vs math-only (392 vs 363 µs) | the min correction for 4 pouches in one vrmpy (sums split into bytes): math ~20% cheaper |
| NPU stopped loading models after ~20 runs | kernel log "failed to map buffer", dma-buf list | the engine never closed its NPU session at exit; on kernel 7.0 each run leaked 4 buffers (~32 MB): sessions are closed at exit now, 0 left behind |
| Board benchmarks 30% low | clock caps | quiet mode: the thermal guard re-applies the quiet caps after every heat step. Lights now have their own switch, the board runs full power with the light off |

## Why it isn't faster still

- CPU and NPU share one memory pipe. The NPU now copies at ~22-23 GB/s on the big 2-bit tracks, the most this chip gives it; running CPU and NPU together gives ~21.8 GB/s in total, no more than the NPU alone.
- What's left on the NPU path is fixed work: attention (~15 ms per word at 768 words in), ~1,100 small ops (~8 ms), and the CPU's share (dictionary shortlist, ~5 ms).
- Prompt reading is compute-bound: one word at a time the kernels are memory-bound, but for many words the vector multiply rate limits. Unpacking each weight once for 4-8 words changed nothing; skipping the per-word result writes would give ~19 words/s.

## Tried and dropped (measured)

- Worker threads spinning between ops instead of sleeping: slower (they steal issue slots from the busy thread).
- Three tile buffers instead of two: no change. A bus bandwidth vote: no change.
- Normalizing float sums after every add: 3% slower, no accuracy change.
- Moving the 16-bit per-layer projection to the CPU: 4% slower, no accuracy change.
- 8-bit chat memory (KV cache) on the CPU: slower (evening test on the Mac).
- Huge pages: the board already runs with transparent huge pages "always".

## Why not "obviously faster" (stopped here, waiting for decisions)

- Talking: attention on the CPU with the rest on the NPU is slower (8.8 / 8.1 vs 9.9 / 9.05: hand-offs). Guessing ahead on the NPU: checking 2 words costs ~1.65x one word, so Token Recycling (1.14-1.28 words per check) still loses.
- The levers left are bytes (more 2-bit tracks after healing), more words per pass (the drafter after fine-tuning), co-op CPU+NPU prompt reading (~+10-20%), and a cheaper dictionary preview.

## Later: CPU and NPU reading prompts together (co-op, LG_COOP=1)

- The NPU alone reads prompts at ~16 tokens/s (vector-multiply bound). For prompt reading, the NPU now computes ~27% of the rows of each big matmul from its tiles while the CPU computes the rest from its own repacked copy and runs every other op; the CPU also quantizes the NPU's inputs (the NPU did that on its scalar units, ~2 ms per matmul). Batches under 32 tokens run CPU-only.
- Bugs found on the way: stale NPU cache lines (shared buffers need compute usage so the NPU drops its copy), memory addresses reused within a graph (input reuse must reset after other ops), a row view of the CPU's repacked weights must carry its buffer.
- Chat server, cooled before each run, both orders: persona reading CPU 30.7-31.2 vs NPU path 35.2 tok/s; a 12-token message 24.2 vs 22.6-23.1; talking 9.08-9.15 vs 8.90-9.22 (same within noise). KL vs CPU 0.0036 (CPU-only small batches: 0).
- Timing trap: consecutive runs heat the board ~4% slower; compare with cooling and alternating order.

### Tried and dropped (measured)

- Two-stage dictionary preview (low-rank first pass): best setting kept the full dice table on 12,326 of 12,733 words vs 12,733 today. Would change what he says.
- Smaller NPU batches (256 / 1024 steps) so packing overlaps: slower (9.44-9.54 vs 9.76).
- Copying step descriptions into cached memory per batch: no change.
- Wider unroll / restrict on GEGLU: no change; it is limited by the float unit (~90 float ops per 32 numbers, both threads share it).
- Backend sampling (--backend-sampling): no gain.
- Host buffers off: within noise.
- Scoring the 1,024 shortlist rows with mul_mat_id: its scratch is sized for every possible expert (~2 GB for 262,144 rows). Context fails.
- A 512-wide attention dot written as one 8-vector pass crashed the NPU program (dspqueue 0x2e) even with a smaller unroll; two 256-wide halves through a shared core works.

### Open at this point

- Every step flushes the NPU cache over its whole output. For the KV write that is the whole chat memory, so it cleans the entire cache 48 times per word. Fix written, not yet measured.
- Run-to-run noise on the board is ~3% even cooled.
